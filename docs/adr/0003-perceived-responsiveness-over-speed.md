# Win on perceived responsiveness, not raw speed

Agent turns are unavoidably slow (tens of seconds; worse when a provider degrades), so v1 invests in *perceived* responsiveness instead of chasing latency. Transport is **plain SSE**, not AG-UI/CopilotKit — a copilot framework is chat-centric and would fight the controls-first, mobile-first UI ([see ADR 0001's instant-action model] and the Q2 UStP), while SSE delivers the same live feed for far less work and no lock-in. During a run we stream two things: **(1) step narration** — each agent tool start/end mapped to a plain-language line ("Searching Naxos beaches… found 8… fetching photos…"), which covers the long tool-heavy middle and is the direct fix for "is it stuck?"; and **(2) streaming assistant text**, which only covers the final compose but is cheap. We explicitly **cut skeleton/placeholder cards** (empty boxes add anxiety and layout shift; the agent batches its output into one end-of-run state snapshot anyway, so true incremental card-fill isn't naturally available) and **defer browse/act-during-run** (state-merge concurrency cost outweighs the benefit when narration already answers the anxiety).

Wait-time engagement content is **prefetched, never live-fetched**: when the user locks a destination during requirement gathering, background calls warm a cache of generic destination content; later waits serve from that cache, falling back to static curated content or already-fetched session content on timeout. Live fetches during a wait are forbidden because they ride the same slow/rate-limited search stack the main task uses — they would arrive late *and* add contention. Progress is shown via narration-driven step count, not a naked stopwatch (a count-up timer amplifies anxiety at 90s).
